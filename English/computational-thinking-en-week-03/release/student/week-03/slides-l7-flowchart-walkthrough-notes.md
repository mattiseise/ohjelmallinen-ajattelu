## Slide 1 — Lesson 7 — Flowchart walkthrough

Frame the walkthrough. Tell students you are going to build one small flowchart shape by shape, from the very first oval to the last. The point is not the umbrella — it is to feel where each shape earns its keep. If the class is moving fast and the live whiteboard sketch is landing, you can skip these slides; if the class wants the slow build, walk through every shape. Ask: "Has anyone ever drawn a flowchart before?" Most have not — set the bar low. ~2 min.

## Slide 2 — Slide 1 — Start

The Start oval. Read it: every flowchart begins with exactly one Start. It marks where the process opens, not what triggers it. Tell students the oval is on purpose — the shape itself signals "this is the entry point" without any extra label. Concrete: an IT support process starts the moment the ticket arrives in the queue — that is what the oval represents. Ask: "What would it mean if a flowchart had two Start ovals?" Answer: two separate processes, which usually means we need two flowcharts. ~3 min.

## Slide 3 — Slide 2 — First step

The first action — one rectangle, one verb. Notice we wrote "check the weather forecast" but did not say *how* (phone, window, radio). That detail is hidden inside the box. This is abstraction at work — the rectangle is the right level of detail for this audience. Concrete IT example: "read the ticket" is one rectangle; the follower's email client is hidden inside. Ask: "What is hidden inside 'check the weather forecast' for you specifically?" Different students will say different things — all valid. ~4 min.

## Slide 4 — Slide 3 — The decision

The diamond. The moment the flat list cannot continue. A diamond holds exactly one yes/no question, with two outgoing arrows — one labelled Yes, one labelled No. Both labels are mandatory; an unlabelled branch leaves the follower guessing. Concrete IT version: "is the user logged in?" has two clear answers and two different responses. Ask: "What is one yes/no question in your IT placement that changes what you do next?" Take two answers. ~4 min.

## Slide 5 — Slide 4 — Both branches

Each branch carries its own rectangles. The Yes path bringing the umbrella; the No path leaving it. The honest test: each branch has to describe what the follower actually does — no skipping a branch because "you would never get there". Concrete IT version: if the user is logged in, close the ticket; if not, ask for a screenshot. Both branches matter. Ask: "What would go wrong if we drew only the Yes branch?" Answer: the follower has no instruction for half the cases. ~4 min.

## Slide 6 — Slide 5 — Closing the flowchart

Both branches meet at one End oval. Every path through a flowchart has to reach an End oval — no loose ends. Count the shapes on the board: one Start, three rectangles, one diamond, one End. Eight shapes total. The whole umbrella process fits on one page, and a literal follower can run it. Ask: "Could the two branches meet at two different End ovals — one called 'left with umbrella' and one called 'left without'?" Yes, absolutely — both are valid. The flowchart is for communication, not for tidiness. ~5 min.

## Slide 7 — Slide 6 — The same shape, an IT example

Same four shapes; new context. The umbrella process is now a help-desk triage. Tell students this is the point: once they have the four shapes, every process they meet at work is just a different filling of the same template. Concrete: a backup script, an onboarding walk-through, an incident-response procedure — all flowcharts with the same four shapes. Ask: "Pick one IT process from your school week. What is its Start oval and what is its End oval?" That question alone is half the work of drawing the flowchart. ~5 min.
